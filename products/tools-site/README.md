# くらしの計算機（広告で収益化する小さなツール集）

登録不要・ブラウザ内だけで動く計算ツール23個の静的サイトです。サーバー費用はほぼゼロで、
問い合わせ対応も発生しない構成にしています。

**トレカ・PSA鑑定**（5個）: PSA鑑定 損益シミュレーター（`psa-profit`）/ 仕入れ上限 逆算（`psa-max-buy`）/
鑑定料の円換算（`grading-fee`）/ トレカ売買の利益率計算（`card-roi`）/
フリマと買取の手取り比較（`furima-vs-kaitori`）

**くらし・仕事**（18個）: 和暦変換 / 年齢計算 / 入学・卒業年 / 日数計算 / 文字数カウント / 割り勘 / 消費税 /
割引・ポイント還元 / 単位変換 / 全角半角 / パスワード生成 / 割合計算（`percent`）/ 時間の足し算・引き算（`time-calc`）/
時給・月給・年収 換算（`hourly-wage`）/ 乱数・抽選（`random`）/ 2・8・10・16進 変換（`base-convert`）/
ひらがな⇔カタカナ（`kana`）/ アスペクト比（`aspect`）

PSA鑑定の費用の式は `pokeca/core.py`（`per_card_costs`・`recommend`）と同じです。画面の初期値（鑑定料・送料・関税など）は
一例で、料金が変わっても計算式は変わらないため、利用者が自分で数字を書き換える前提にしています。
「フリマと買取の手取り比較」の式と端数処理（1円未満切り捨て）は `products/kaitori-kit/tejori.py` の売り手の視点と同じです。
手数料率・送料・買取率の初期値は一例で、実在のサービス名・店名は出していません。

扱わないと決めているもの: 規格値の正しさを保証できないもの（スリーブのサイズ表など）、医療系（BMIなど）、
金融商品の計算（ローン返済など）。

### 検索・SNS 向けの情報（`build.py` の `page` が全ページに出す）

- `<head>`: `description`（ページごとに別の文。空や重複があるとビルドが止まる）、`canonical`、OGP（`og:title` / `og:description` / `og:type` / `og:url` / `og:site_name`）、
  `twitter:card`、`theme-color`（ライト/ダーク。色は `src/style.css` の `--bg` から取る）、favicon（`public/favicon.svg` をビルド時に生成）。
  `canonical` と `og:url` は `site.json` の `url` から作ります。
  CSS・JavaScript・favicon と内部リンクは、`url` のパス部分（ベースパス。いまは `/toto`）を前に付けた絶対パスで出します。
- `og:image` は、`site.json` に `og_image` を足したときだけ出ます。値は `https://` のURLか、`src/` に置いた画像のファイル名（ビルド時に `public/` へコピー）。
- 構造化データ（JSON-LD）: トップに `WebSite`、各ツールに `WebApplication`（無料であることだけ）、解説記事に `Article`、トップ以外に `BreadcrumbList`（早見ページはこれだけ）。
  評価（`aggregateRating`）・公開日・著者など、確かめられない値は入れていません。

無料のトレカ向けツール → 解説記事 → 商品紹介ページ → 外部の販売サイト、という流れです。このサイトでは販売・決済をせず、
購入者とのやりとりも発生しない前提です（紹介ページに「サポートなし」「返金は販売サイトの規定」と明記）。

解説記事は「計算の考え方」だけを書いています。料金・関税・税率の実際の額や制度は確認していないため書いていません。
記事内の計算例は `build.py` の `DEF`（ツールの初期値）と `EX`（仮の売値）から計算しているので、初期値を変えると記事の数字も変わります。
記事の本文は `build.py` の `GUIDES`、ツールごとに出す記事は `TOOL_GUIDES`、紹介ページの本文は `sheet_body` にあります。

### 早見ページ（`/born/`・`/era/`）

「1990年生まれ 履歴書」「昭和50年 西暦」のような検索に1ページで答えるための、自動生成のページです。

- **載せるのは計算で出せる値だけ**です: 年齢、干支、和暦と西暦の対応（改元のあった年は月日つき）、入学・卒業年、節目の年。
  その年の出来事・有名人・流行・運勢など、確認していない情報は載せません。
- 節目は、年の決め方を1行で書けるものだけです: 還暦（満60歳になる年＝数え年61歳）、古希・喜寿・傘寿・米寿・卒寿・白寿
  （数え年70・77・80・88・90・99歳。満年齢で数える場合の年も並べる）、年男・年女（生まれ年と同じ十二支の年）。
  厄年は数え方が神社や地域で違うので載せていません。定義は `src/lib.js` の `LONGEVITY` にあります。
- 入学・卒業年の表は、4月2日〜12月31日生まれと1月1日〜4月1日生まれ（早生まれ）の2つを並べます。
  1940年以前の生まれ（いまの学校制度が始まった1947年より前に小学校へ入学する年代）には表を出しません（`src/hayami.mjs` の `SCHOOL_SYSTEM_FROM`）。
- 和暦の年のページで年齢を出すのは、生まれ年ページのある1926年以降だけです。
- **計算は Python で書き直していません。** `build.py` の `build_hayami` が `node src/hayami.mjs <年> <月> <日>` を1回呼び、
  `src/lib.js` の関数（`warekiOfYear`・`ageInYear`・`schoolYears`・`milestones`・`hayamiNow` など）の結果を JSON で受け取って HTML に流し込みます。
  そのため、**ビルドには Node.js が必要**です（無ければ理由を表示して止まります）。期待値のテストは `src/test.mjs` の「早見ページ」にあります。
- 和暦の年のパスを `/wareki/<元号>/<年>/` にしなかったのは、`/wareki/` が変換ツールのページで、一覧ページの置き場所とパンくずが重なるためです。
- title・description はページごとに別の文で、既存の重複チェック（重複があるとビルドが止まる）の対象です。sitemap.xml にも全ページが入ります。

**年が変わったら再ビルドが必要です。** 理由は2つあります。

1. 対象の年の範囲がビルドした年までだから（年が変わると `/born/<新しい年>/` と `/era/reiwa/<新しい年>/` が増える）。
2. 「今年の年齢」などはビルド時点の値を HTML に書いているから。ページには「2026年11月時点」のように時点を明記し、
   JavaScript が動けば開いた日の値に上書きします（`src/app.js` の `hayami`）。ただし description の年齢と、JavaScript を使わない閲覧・検索エンジンが読む値はビルド時点のままです。

年が変わったあと再ビルドしていないと、`python build.py --check` が［要対応］として知らせます。
将来の年の和暦は「令和が続いた場合」として計算し、その旨をページに書いています。改元があったら `src/lib.js` の `ERAS` と `ERA_SLUGS` に足して再ビルドします。

### 商品紹介ページの設定（`site.json`）

| 項目 | 使い方 |
|---|---|
| `product_url` | 販売ページのURL（`https://...`）。**空のあいだは購入ボタンを出さず「販売準備中」と表示**する。販売を始めたら入れて `python build.py` |
| `product_price` | 価格の表示文字列（例: `"980円（税込）"`）。書いたとおりに表示する。空なら価格を表示しない |
| `product_verified` | 実機で動作確認した環境（例: `"Excel（バージョン）/ Googleスプレッドシート（確認日）"`）。空のあいだは「Excel と Googleスプレッドシートの実機では未確認」と表示する。**確認していない環境は書かない** |

商品画像は、ビルド時に `products/psa-sheet/dist/images/*.png` があれば、幅1200pxに縮小した WebP（品質90）にして `public/sheet/` に出力し、表示します（ファイル名順、1枚目が先頭）。
元の PNG は変更しません。縮小には Pillow を使い、Pillow が無い環境では警告を出して縮小せずに PNG のままコピーします。
無ければ画像なしのページになります。紹介ページの文章（同梱物・対応環境・注意書き・FAQ抜粋）は `products/psa-sheet/` の
`listing.md`・`README.md`・`FAQ.md`・`make_zip.py` に合わせて手で書いたもので、自動では同期しません。商品側を変えたら `sheet_body` と `SHEET_FAQ` も直してください。

## PSA10 買取価格の比較（`/kaitori-price/`。いまは生成しない設定）

買取店が自分のサイトで公開している PSA10 の買取価格を、カードごとに引用して並べるページ群です。
**`site.json` の `kaitori_price.publish` が `false` のあいだは1ページも生成されず、トップからのリンクも出ません。**
公開するかどうかはオーナーが決めます（下の「規約の確認結果」を読んだうえで）。

### 規約の確認結果（2026-11-27 に各店のサイトで読んだもの）

| 店 | 読んだページ | 該当する記述 | 掲載 |
|---|---|---|---|
| シンソク | `shinsoku-tcg.com/kiyaku`（利用規約）、`/kaitori-kiyaku`（買取規約） | 利用規約 第5条（禁止事項）「本サービスによって得られた情報を商業的に利用する行為」。自動取得・転載を名指しした条項は無し | **載せない**（広告で収益化するサイトへの掲載は「商業的に利用」に当たると判断） |
| トレカバンク | `store.torecabank.com/terms`（利用規約） | 第5条（禁止事項）「本サービスによって得られた情報を商業的に利用する行為」（シンソクと同じ文） | **載せない**（同上） |
| トレカクラブ | `torecaclub.com/terms/`（利用規約 全25条）、`/article/guide/`、`/robots.txt` | 転載・二次利用・自動取得を禁じる条項は見当たらない。第18条（禁止行為）は「虚偽登録、…不正アクセス、システムへの妨害…」。価格については第7条「当社の価格表示に客観的に明白な誤記が判明したときは、速やかに理由と訂正内容を説明します」 | 載せる |
| トレカラウンジ | `kaitori.toreca-lounge.com/purchase-terms`（買取注意事項）、`/legal/privacy`、`/legal/tradelaw`、`/robots.txt` | **サイトの利用規約にあたるページは見つからなかった**（フッターにあるのは左の3つだけ）。読んだページに転載・自動取得の記述は無い。価格については「表示価格はあくまで参考価格となります」 | 載せる設定にしているが、**根拠が弱い**（禁止は書かれていないが、許可も書かれていない） |

- 「商業的に利用」の条項は、文面上は登録ユーザー向けの禁止事項です。登録せずに公開ページを読むだけの場合に及ぶかは
  はっきりしませんが、安全側に倒して載せていません。この2店には取得もしません（`kaitori.py` は掲載が「入」の店だけ取得する）。
- どの店の規約も、こちらが読んだ日の内容です。規約は変わるので、公開を続けるなら時々読み直してください。
- 規約に書かれていなくても、店から申し出があれば外します（下の「店を外す」）。そのために `contact`（連絡先）が要ります。

### 載せるカードの条件（`kaitori.py` の `select`）

保守的にしています。満たさないカードは黙って落とします（2026-11-27 の取得では、2店合計 1,182 行から 335 枚）。

1. 掲載が「入」で、その回の取得に成功した店の、PSA10 の行だけ。
2. カード番号とカード名（レアリティ表記・括弧書きを除く）が一致する行だけを同じカードとみなす（`pokeca/core.py` の `card_key`）。
3. 括弧書きの注記（1ST、ミラー仕様、言語、配布元など）まで含めた名前が店どうしで違うものは載せない。
4. 1つの店の中で同じカードに違う価格が2つ以上あるものは載せない。
5. 2店以上に価格があるカードだけ（1店だけのカードのページは作らない）。
6. 店どうしの価格が2倍を超えて離れているものは、別のカードを結び付けた疑いがあるので載せない。

当初の案は「3店以上で一致」でしたが、規約上載せられる店が2店だったので、代わりに 3・4・6 を足しています。

### ページに書くこと・書かないこと

- 各ページの上部に、取得日時と「実際の買取価格は、各店の最新の表示と査定で決まります」を出す。
- 取得から48時間を過ぎたら「価格が古い可能性があります」を出す（ビルド時に判定し、ページを開いたときにも `app.js` が判定し直す）。
  14日を過ぎたデータでは、比較ページを生成しない。
- 店ごとに、出典（その店の掲載ページ）へのリンクと取得日時を出す。店頭・郵送の別も出す。
- 取得に失敗した店は「取得できませんでした」と出し、ほかの店だけで生成する。
- 店のロゴ・画像・カード画像は使わない。各店と提携していないことを書く。
- 買取の勧誘、特定の店を勧める文、「必ず」「最高値」などの断定は書かない。

### データの更新（`kaitori.py`）

```bash
python kaitori.py           # 掲載が「入」の店から取得して kaitori-data/prices.json を更新（requests が必要）
python build.py             # publish が true なら /kaitori-price/ を生成
```

- 取得の中身（1.5秒間隔、上限ページ数、ページの読み方）は `pokeca/shops/` をそのまま呼んでいます。
  トレカラウンジは PSA10 の一覧だけを読みます。2026-11-27 の取得は2店で約20ページ、30秒ほどでした。
- **取得は1日1回まで。** 前回の取得（失敗した回も含む）から20時間たっていないと、取得せずに終わります（`--force` で無視）。
- 取得できた店が2店未満（全店失敗を含む）なら、**前回のデータを残します**（空のページで上書きしない）。
- 置き場所が `data/` でないのは、リポジトリの `.gitignore` が `data/` を除外しているためです。

### 公開する手順（オーナーが決めたら）

1. `site.json` の `contact` に連絡先を入れる（店が取り下げを申し出る先。空だと `python build.py --check` が［要対応］を出す）。
2. `site.json` の `kaitori_price.publish` を `true` にして既定ブランチに入れる → `pages.yml` が比較ページつきで公開する。
   この時点のデータはコミット済みの `kaitori-data/prices.json`（取得から48時間を過ぎていれば「古い可能性」の表示つき）。
3. 毎日更新するなら、`.github/workflows/kaitori-price.yml.disabled` の名前を `kaitori-price.yml` に変える
   （GitHub の画面でファイルを開き、鉛筆 → ファイル名を書き換えて Commit。スマホのブラウザでもできる）。
   毎日 04:17（日本時間）に 取得 → `prices.json` をコミット → ビルド → 公開 を行う。
   最初に **Actions → 「買取価格の比較ページを毎日更新して公開」→ Run workflow** で1回動かし、各店から取得できているかログで確かめる
   （GitHub のサーバーからのアクセスを店側が受け付けるかは未確認）。
   コミットに失敗する場合は、Settings → Actions → General → Workflow permissions を「Read and write」にする。
4. 止めるときは、ファイル名を `.disabled` つきに戻す。ページごと消すなら `publish` を `false` に戻す。

### 店を外す（店から申し出があったとき）

`site.json` の `kaitori_price.shops` で、その店を `false` にして既定ブランチに入れるだけです。

```json
"kaitori_price": { "publish": true, "shops": { "トレカクラブ": true, "トレカラウンジ": false, "シンソク": false, "トレカバンク": false } }
```

- 次のビルドから、その店の価格・店名・リンクはどのページにも出ません（取得済みのデータに残っていても出さない）。以後その店には取得もしません。
- **いまは載せている店が2店なので、どちらかを外すと比較できるカードが0枚になり、比較ページは1枚も生成されなくなります。**
- すぐ全部消したいときは `publish` を `false` に。
- 店を足すとき（規約を読んで載せてよいと確かめた場合だけ）は `true` にします。名前は `pokeca/shops/` の店名（`kaitori.py` の `MODULES`）。

### 分かっている弱点

- 載せている店が2店だけで、うち1店は利用規約のページが無い（上の表）。
- 価格は取得した時点のもの。毎日更新を有効にしないと、48時間後から全ページに「古い可能性」が出て、14日後に生成されなくなる。
- 五十音順は、かな・カナの文字順。漢字で始まるカード名は読みの順にならない。
- カードごとのURLは日本語を含む（`/kaitori-price/201-165-リザードンex/`）。照合キーから作るので、店の表記が変わるとURLも変わる。
- テストは `tests/test_kaitori_price.py`（架空のデータ。照合の条件、古いデータの表示、店の入・切、失敗時の扱い）。

## 公開の手順（GitHub Pages）

公開先は GitHub Pages のプロジェクトページ **https://n0619y.github.io/toto/** です（`site.json` の `url` に設定済み）。
`.github/workflows/pages.yml` が、既定ブランチに `products/tools-site/` の変更が push されるたびに、
テスト（`node src/test.mjs`）→ ビルド（`python build.py`）→ 公開 を自動で行います。ビルドした `public/` をコミットし直すことはしません。

本人のアカウントで行うのは次の2つだけです（どちらもスマホのブラウザでできます）。

- [ ] リポジトリの **Settings → Pages → Build and deployment → Source** を **GitHub Actions** にする（最初の1回だけ）。
      無料プランでは、Pages を使えるのは公開（public）リポジトリだけです。
- [ ] 変更を既定ブランチに入れる（または **Actions → 「tools-site を GitHub Pages に公開」→ Run workflow** で手動実行）。
      数分後に https://n0619y.github.io/toto/ で開けることと、存在しないURL（例: `/toto/nai/`）で 404 ページが出ることを確かめる。

そのあと、任意で:

- [ ] `site.json` の `operator`（運営者名。ペンネーム可）と `contact`（連絡先。プライバシーポリシーのページに表示）を入れる。
      いまは `operator` が初期値、`contact` が空のままで、`python build.py --check` が［要対応］として知らせます（公開そのものは止まりません）。
- [ ] SNS で共有されたときの画像を用意し、`site.json` に `og_image` を足す。
- [ ] Google Search Console に `https://n0619y.github.io/toto/` を「URL プレフィックス」で登録し、`https://n0619y.github.io/toto/sitemap.xml` を送信する。
- [ ] **Google アドセンス**は独自ドメインが前提です（`github.io` のままでは申請できない想定）。独自ドメインに切り替えてから申請し、
      承認されたら `site.json` の `adsense_client` に `ca-pub-...` を入れる → 全ページに広告枠が入る。

### 置き場所の階層（ベースパス）

`build.py` は、`site.json` の `url` のパス部分をベースパスとして使います。`https://n0619y.github.io/toto` なら `/toto`、
`https://example.com` なら空（ドメイン直下）です。内部リンク・CSS・JavaScript・画像・favicon の参照（`/toto/style.css` など）、
canonical・og:url・sitemap.xml・構造化データのURLは、すべてここから作られます。`404.html` もベースパスつきの絶対パスで出すので、
どの階層のURLで表示されても壊れません。`public/.nojekyll` は GitHub Pages に Jekyll の処理をさせないためのファイルです。

注意: クローラーが読む `robots.txt` はドメイン直下（`https://n0619y.github.io/robots.txt`）だけなので、プロジェクトページでは
`/toto/robots.txt` は読まれません（sitemap は Search Console から送信します）。独自ドメインにすれば読まれます。

### 独自ドメインに切り替える場合

`site.json` の `url` を新しいURL（`https://` から、末尾の `/` なし。例: `https://example.jp`）に書き換えて再ビルドするだけです
（push すればワークフローが再ビルドします）。リンクやファイルの参照は自動で `/` 始まりに戻ります。
GitHub Pages のまま独自ドメインを使うなら Settings → Pages の Custom domain に設定します。
Cloudflare Pages などに移すなら、公開ディレクトリを `products/tools-site/public` にします（その場合はホスティング側で
`pip install pillow && python build.py` を実行するか、ビルド済みの `public/` をコミットします）。

手元で確かめるときは、`url` のパスと同じ名前のディレクトリの下に `public/` を置いて配信します
（例: `toto` → `public` のリンクを作り、その親で `python -m http.server`、`http://localhost:8000/toto/` を開く）。

`--check` の［任意］は、空のままでも公開できる項目です（広告ID、`og_image`、商品の販売URL・動作確認の環境）。

審査には数日〜数週間かかり、落ちることもあります。検索からの流入が増えるまで数か月は収益ゼロの想定です。

## 開発

```bash
node src/test.mjs     # 計算ロジックのテスト
python build.py       # public/ を再生成（早見ページの計算に node を使う。全292ページで2秒ほど）
python build.py --check   # 公開前に直すべき項目の一覧（生成はしない）
```

ツールを増やすときは `src/lib.js`（計算）・`src/test.mjs`（手計算した期待値のテスト）・`src/app.js`（画面）に足し、
`build.py` の `CARD_TOOLS`（トップの「トレカ・PSA鑑定」）か `LIFE_TOOLS`（「くらし・仕事」）に1件足します。
トレカ向けツールを足したときは、下部に出す解説記事を `TOOL_GUIDES` にも足します。
